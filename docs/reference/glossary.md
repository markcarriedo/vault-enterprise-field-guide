# Glossary

Terms as we encounter them.

| Term | Meaning |
|---|---|
| Seal | The process that protects Vault's encryption key; must be "unsealed" before Vault can operate. |
| Auto-unseal | Delegating unseal to an external KMS (here, AWS KMS) instead of manual key shards. |
| Storage backend | Where Vault persists its encrypted data (e.g. Integrated Storage/Raft, Consul). |
| Integrated Storage | Vault's built-in Raft-based storage backend — no separate Consul cluster needed. |
| HVD | HashiCorp Validated Design — HashiCorp's published reference architectures and Terraform modules for deploying its products in production. |
| Conventional Commits | A commit message convention (`type(scope): summary`, e.g. `docs:`, `feat:`, `fix:`) that tools like git-cliff parse to generate changelogs automatically. |
| Raft | The consensus protocol behind Integrated Storage — how the Vault nodes replicate data and elect a leader. |
| Recovery keys | Generated by `operator init` when auto-unseal is in use, instead of Shamir unseal keys. Not needed for routine unsealing (that's automatic via KMS) — used for operations like regenerating the root token. |
| Root token | The initial, all-powerful auth token generated by `operator init`. Fine for early sandbox testing; not something to keep using once real auth methods/policies exist. |
| SSM / Session Manager | AWS Systems Manager's mechanism for shell access and port-forwarding to EC2 instances without SSH keys or open inbound ports — how this cluster is reached, with no bastion host. |
| Private hosted zone | A Route53 DNS zone that only resolves within its associated VPC(s) — doesn't validate domain ownership, unlike a public zone. |
| Static secrets | Secrets that exist independently of Vault — you put a value in, Vault stores/versions/controls access to it (the KV secrets engine). Contrast with dynamic secrets, which Vault generates on demand. |
| KV v2 | Vault's versioned key-value secrets engine — every write creates a new version rather than overwriting, with metadata (created time, deletion state) tracked per version. |
| ACL policy | Path-based access rules (`path "secret/data/x/*" { capabilities = [...] }`) attached to tokens/identities — Vault's core authorization mechanism. |
| Namespace | An Enterprise feature: a fully isolated administrative boundary (own policies, auth methods, secrets engines, audit) within one physical cluster — see [Patterns](patterns.md). |
| Auth method | A way to prove identity to Vault and receive a token with policies attached — the root token isn't one; AppRole and AWS auth are. |
| AppRole | An auth method built around a `role_id` (like a username) and `secret_id` (like a password) — needs a trusted way to distribute the `secret_id` safely. |
| AWS auth method | An auth method where an EC2 instance authenticates using its own IAM role identity (a signed STS `GetCallerIdentity` request) — no separate secret to generate or distribute. |
| Dynamic secrets | Credentials Vault generates on demand and tracks with a lease, rather than storing a value someone already created — contrast with static secrets. |
| Lease | The record Vault keeps of a dynamic secret's lifetime (TTL, renewability) — what `vault lease revoke` acts on. Revoking the lease doesn't always mean the underlying credential dies immediately; depends on the secrets engine and credential type. |
| assumed_role (AWS secrets engine) | A dynamic-credential mode where Vault assumes an existing IAM role via STS and returns the temporary credentials — no IAM users created or deleted. Revocation is soft: AWS STS has no general API to invalidate an already-issued session before its own TTL. |
| iam_user (AWS secrets engine) | A dynamic-credential mode where Vault creates a real IAM user + access key per lease and deletes it on revocation — true immediate revocation, at the cost of granting Vault's own identity IAM user-management permissions. |
| Audit device | Vault's record of every request/response — `file`, `syslog`, or `socket`; no native CloudWatch option. Sensitive fields are HMAC-hashed by default, not written in the clear. |
| SSM State Manager | AWS Systems Manager's mechanism for applying a document (install a package, run a config) to a fleet of instances by tag, on a schedule — used here to install/configure the CloudWatch Agent without touching the Vault nodes' own launch template. |
| CloudWatch Agent | AWS's agent for shipping logs/metrics from an EC2 instance to CloudWatch — not preinstalled on the HVD module's AMI, and only *configures* (doesn't install) via the `AmazonCloudWatch-ManageAgent` SSM document. |
| Raft snapshot | A point-in-time capture of Integrated Storage's entire Raft state (`vault operator raft snapshot save`), restorable cluster-wide (`vault operator raft snapshot restore`) — the disaster-recovery mechanism for a Raft-backed Vault cluster. Streams to wherever the CLI runs, not to the server. |
| Automated snapshot agent | A Vault Enterprise feature that periodically pushes Raft snapshots to cloud storage on its own, configured via the Vault API rather than a Terraform resource — not used here in favor of a manual save/upload flow; see the [decision log](decisions.md). |
| Root token regeneration | Replacing the root token without needing the old one, using a quorum of recovery (or unseal) key shares instead — `vault operator generate-root`. Since Vault 2.0 the endpoint also requires an authenticated token, not just key fragments. |
| Nonce (generate-root) | A value returned when starting `vault operator generate-root -init`, submitted alongside every recovery/unseal key share to tie separate submissions together into the same generation attempt. |
| OTP (generate-root) | A one-time value returned by `vault operator generate-root -init`, used to decode (XOR-unwrap) the final generated token — Vault generates it automatically as of 0.11.2, no separate `-generate-otp` step needed. |
| Autopilot | Vault Integrated Storage's automated cluster-management feature — tracks server health, promotes/demotes voters, and (if `cleanup_dead_servers` is enabled, and the node has been unreachable past `dead_server_last_contact_threshold`) removes dead servers from the Raft peer list. This build manages it via Terraform (`vault_raft_autopilot`, `cleanup_dead_servers = true`, `min_quorum = 3`); the removal threshold is still the 24h default. |
| Redundancy zone | An Autopilot feature that groups nodes by availability zone, promoting a non-voting spare in a zone automatically if that zone's voter fails. This build runs one node per AZ with no spares (`zone-voter` type), so there's nothing to promote if a zone's own node dies. |
| zone-voter | An Autopilot server type: the single voting node responsible for its availability zone under the redundancy-zone feature, as opposed to a non-voting spare in the same zone. |
| dead_server_last_contact_threshold | The Autopilot setting (default 24h) that actually gates automatic peer removal — a server's `NodeStatus` only flips from `alive` to `failed` (eligible for pruning) after this long without contact. `cleanup_dead_servers = true` alone does not make removal prompt; HashiCorp recommends keeping this threshold high to avoid pruning a briefly-unreachable node. |
| Transit | Vault's encryption-as-a-service secrets engine — an app sends plaintext to `transit/encrypt/<key>` and gets ciphertext back (and vice versa for decrypt), without ever holding or seeing the actual encryption key. |
| Versioned key (Transit) | Every Transit key rotation adds a new version rather than replacing the key outright — old ciphertexts (tagged `vault:vN:...`) keep decrypting under their original version, while new encryptions move to the latest one automatically. |
| exportable (Transit) | A one-way key flag (cannot be disabled once set) required — alongside explicit `read` access on `transit/export/<type>/<name>` — before Vault will ever return a Transit key's raw bytes. Left `false` by default; this build never sets it. |
| PKI secrets engine | Vault as a certificate authority — issues short-lived leaf certificates on demand from a role (`pki_int/issue/<role>`), rather than storing a pre-existing long-lived one. |
| Root CA vs. intermediate CA | HashiCorp's recommended PKI topology: a root mount that only ever signs an intermediate's CSR, and an intermediate mount that does all real leaf-certificate issuance — so routine issuance traffic never touches the CA's actual trust anchor. |
| CSR (certificate signing request) | An unsigned request for a certificate, containing the requester's public key and identity info — what an intermediate CA generates and sends to the root to be signed, without ever exposing the intermediate's private key to the root. |
| CRL (certificate revocation list) | A signed, published list of a CA's revoked certificate serial numbers — how a client checks whether an otherwise-valid, unexpired certificate has actually been revoked. |
